In plain words

Eight terms you'll hear — decoded.

You don't need to be technical to understand or demo this. Here's what each word means, in one line — with the engineering detail underneath if you want it.

MCP Model Context Protocol

The standard plug socket that lets an AI assistant use real tools instead of only talking. Think USB, but for AI.

Under the hood — an open JSON-RPC spec for tool discovery and invocation, now supported by Claude Code, Cursor, Windsurf, Gemini CLI and Codex.

MCP server what MailMan is

A small program that plugs into that socket and offers a set of abilities. MailMan's abilities are all about email.

Under the hood — a Node.js stdio server your editor spawns per session via npx -y @integratex/mailman. No daemon, no port, no cloud.

Tool one thing the AI can do

Each ability is a separate, named tool — “draft an email”, “search the inbox”. MailMan ships 23 of them.

Under the hood — each returns plain JSON, so any MCP host renders it its own way. Errors are structured { code, message }, not prose.

Draft → confirm the safety flow

MailMan prepares the email and shows it to you first. A second, separate step actually sends it — only after your “yes”.

Under the hood — draft_email creates a short-lived draft (10-min TTL); confirm_send is the only tool that dispatches mail, and it's idempotent.

App Password the simple login

A 16-character code Google gives you for one specific app. Your real password is never involved and you can revoke it any time.

Under the hood — used for SMTP/IMAP. Google disabled plain-password SMTP login in 2022, so this or OAuth2 are the only options.

OAuth2 the passwordless login

“Sign in with browser.” You approve access on Google's own page — useful if you use passkeys or your admin turned App Passwords off.

Under the hood — your own Google Cloud Desktop app client, loopback redirect, refresh token stored encrypted. Unlocks the Gmail REST API and Contacts.

OS keychain where secrets live

The vault your operating system already uses for passwords. MailMan keeps its encryption key there — never in a file you could accidentally copy.

Under the hood — macOS Keychain / Windows Credential Manager / Linux Secret Service via keytar; AES-256-GCM over the stored account file.

Template a tone, not a form letter

182 ready message types — FYI, follow-up, EOD report, apology. They shape the tone; the AI still writes the actual words for your situation.

Under the hood — a template is a subject prefix + a one-line structural hint across 23 categories. Only fwd/reply are mechanical.

How MailMan works

Two doors, one safety gate.

The single most important idea: you type commands to set things up, and your AI handles everyday mail. Anything sensitive stays out of the AI's reach by design.

🗣️

The AI door

Send, read, search, schedule — all in plain English, from inside your editor. This is the door you use every day.

“mailman, email this build to the QA team.”

⌨️

The terminal door

Setup, accounts, credentials, diagnostics. Only you can open this one — the AI has no access to it at all.

mailman init, mailman doctor

🛑

The safety gate

Between “compose” and “sent” sits an explicit confirmation. Nothing leaves your machine until you approve the preview.

Preview shows From, To, Subject, attachments and signature.

🔌

Where it runs

On your machine, nowhere else. Your editor starts MailMan when a session begins and stops it when the session ends. There is no MailMan cloud, no account to create, and no server holding your mail.

Under the hood — stdio JSON-RPC between host and server; Gmail is reached over SMTP/IMAP (App Password) or the Gmail REST API (OAuth2), normalised to one output shape.

🔐

How your credentials are held

Encrypted, and bound to this machine. Copy the config file to another computer and it's useless ciphertext — MailMan there refuses to decrypt rather than quietly degrade.

Under the hood — AES-256-GCM over accounts.json; the master key lives in the OS keychain via keytar. Every call appends to a local activity.log — tool name and metadata only, never bodies or secrets.

Quick start

From nothing to sending mail — about 30 seconds.

Two commands and a restart. You'll need a Gmail address and either a Google App Password (fastest) or the browser sign-in option the wizard offers.

Install it globally

One package, one binary. Use whichever package manager you already have.

# npm
npm install -g @integratex/mailman

# or pnpm / yarn / bun
pnpm add -g @integratex/mailman
yarn global add @integratex/mailman
bun add -g @integratex/mailman

It adds your Gmail account, encrypts the credentials into your OS keychain, and writes the MCP config into whichever AI tools you tick. Safe to re-run any time.

Something not working? One command tells you why

doctor runs a live login for every configured account plus a full environment pre-flight — so a password revoked last week surfaces here, not on your next silent send. 

mailman doctor        # live checks: keychain, Node, Gmail reachability, logins
mailman status        # what's configured right now
mailman register -i   # add more AI tools later
🧩 Prefer to wire it up by hand? The MCP config carries no secrets — credentials live in your OS keychain, so this block is safe to commit or share: { "mcpServers": { "mailman": { "command": "npx", "args": ["-y", "@integratex/mailman"] } } }. 🎯

Picking tools from the terminal

Register some now and more later — it's idempotent, so re-running is always safe. 

mailman register --tools claude,cursor
mailman register --tools all --scope global
mailman register -i        # interactive picker
mailman register           # just print the claude one-liner

Gemini CLI, Windsurf and Codex ignore --scope — they only support a single user-level config, so MailMan writes there regardless.

⚠️ Two things people assume wrongly. “Claude” means Claude Code, the CLI — the Claude Desktop app is a separate host and is not auto-registered; paste the block into its config yourself. And “OpenAI” means Codex, OpenAI's CLI — the ChatGPT app isn't a stdio MCP host, so there's nothing to register there.
🔁 Always restart the AI tool after registering. MCP servers are spawned per session, so a running session keeps the old configuration.

list_scheduled Scheduling Pending, sent and failed scheduled sends with attempt counts.
cancel_scheduled Scheduling Cancel a queued send before it fires.
list_recent_emails Reading Recent inbox or sent mail, paged. Limit capped at 50 to bound context cost.
read_email Reading Full body and metadata for one message; bodies capped at ~20k chars with a truncated flag.
search_emails Reading Search inbox, sent or all mail. OAuth2 gets Gmail's full query syntax; App Password a simpler subset.
get_mailbox_overview Reading Sent + inbox + unread and attachment counts in a single call.
suggest_recipients Contacts Ranked address candidates for a partial name; flags ambiguity instead of picking.
list_contacts Contacts The full address book, merged with Google Contacts on OAuth2 accounts.
add_contact Contacts Add an address to the local book manually.
remove_contact Contacts Remove an address from the local book.

configure_account Accounts Add or update an account; credentials are verified with a live Gmail login before anything is stored.
update_account_profile Accounts Change the “From Name” or signature without touching encrypted credentials.
remove_account Accounts Delete an account; gated by confirmRemoval if it's the default or the last one.
get_settings Settings Current globals — default account, draft TTL, body type, notifications.

get_status Diagnostics Configured accounts, security state, MCP registration and recent activity counts.

Questions you'll get asked

Straight answers.

The concerns that come up every time — and what to say.

“Can the AI send an email without me knowing?”+

No. Sending is split across two separate tools. draft_email can only prepare and preview; confirm_send is the only thing that actually dispatches mail, and it needs the id of a draft you've been shown. This is a structural split in the code, not a polite instruction in a prompt — so there's nothing for a model to skim past or be talked around.

“Where do my Gmail credentials go?”+

Into an encrypted file on your own machine, with the encryption key held in your operating system's native store — macOS Keychain, Windows Credential Manager, or the Linux Secret Service. They are machine-bound: copy the config to another computer and it decrypts to nothing. Nothing is transmitted anywhere except directly to Google when you send or read mail. There is no MailMan server.

“Why can't I just use my Gmail password?”+

Google removed that option in 2022 — regular passwords no longer work for SMTP or IMAP at all. Your two choices are an App Password (a 16-character code scoped to one app, revocable from your Google account page — the default and simplest path) or OAuth2 browser sign-in, which is what you want if you use passkeys or your Workspace admin disabled App Passwords. The setup wizard offers both on the first screen.

“Does it read my whole mailbox?”+

It can — reading the inbox is half the point of the product — but only when a tool is called, and only the messages that call asked for. Nothing is indexed, synced, cached or uploaded. Every call is appended to a local activity.log recording the tool name and non-sensitive metadata; message bodies and credentials are never logged. If you only want to send, simply never ask it to read.

“Which AI tools does it work with?”+

Five are configured for you by mailman init / mailman register: Claude Code, Cursor, Gemini CLI, Windsurf and Codex. Beyond those, MailMan is a standard stdio MCP server — any MCP-capable host works once you paste the config block in, including Claude Desktop, Zed, Cline and Continue. Its tools return plain JSON with no host-specific formatting, precisely so every host can render them its own way. Note that “Claude” here means Claude Code, the CLI — the Claude Desktop app is a separate host and isn't auto-registered. See Works with for the full table and config paths.

“Only Gmail? What about Outlook or our company mail server?”+

Gmail and Google Workspace today — both via App Password (SMTP/IMAP) and OAuth2 (Gmail REST API). Generic SMTP/IMAP providers aren't supported in v1.1.2. It's a reasonable feature request; open an issue on GitHub and say which provider, since the transport layer is already abstracted behind an account "method".

“Is it really free? What's the catch?”+

MIT-licensed, free for commercial use, no account, no telemetry, no paid tier. The catch — such as it is — is that you supply the Gmail account and, if you choose OAuth2, your own Google Cloud client. MailMan is plumbing between your AI and your mail; it never sits in the middle as a service.

“What happens if the send fails, or I retry?”+

Failures come back as structured errors your AI can act on — it re-asks you on an ambiguous account, backs off on a rate limit, tells you plainly on a bad credential. And confirm_send is idempotent: calling it again with the same draft after a successful send returns the original result rather than mailing twice. Scheduled sends retry to a cap and are marked failed, never silently dropped.

“I'm on Linux / on a headless server — does it work?”+

Yes, with one requirement: Linux needs a running Secret Service provider (gnome-keyring or kwallet) so credentials can be stored properly. If there isn't one, setup fails with instructions rather than falling back to plaintext. For OAuth2 on a box with no browser, auth login prints the consent URL plus an ssh -L tunnel command to complete it from your laptop. See CROSS-OS.md.

“Why is there a mcp-mailman command too?”+

Because GNU Mailman — the mailing-list manager — already ships a /usr/bin/mailman on some Linux servers. Both names point at the same binary; use mcp-mailman on such a host to be unambiguous. Everywhere else, mailman is the name to use. The npm package itself is @integratex/mailman.

🛠️ Contributing — anyone can open a PR

You don't need commit access. Fork it, branch, push to your fork, open a pull request — the standard GitHub flow. TypeScript, strict mode, no build magic, and the whole development loop is four scripts. Full detail in CONTRIBUTING.md. 

# 1 · fork on GitHub, then clone your fork
git clone https://github.com/<you>/mailman.git
cd mailman && npm install
#     Linux also needs: sudo apt-get install -y libsecret-1-dev

# 2 · branch for the change
git checkout -b fix/imap-quoted-printable

# 3 · the loop — exactly what CI runs
npm run dev         # run the MCP server from source
npm run lint        # eslint
npm run typecheck   # strict tsc, no emit
npm test            # node --test via tsx

# 4 · push to your fork and open a PR against main
git push -u origin fix/imap-quoted-printable

Green local run = green PR. CI on every pull request runs lint, typecheck, build and tests on Node 20 — the same four commands. A PR template walks you through the rest.

Good first contributions: a new message template or category (plain data in src/mail/templates.ts), an extra AI tool in the register command (one entry in EDITORS), a docs fix, or a CROSS-OS.md note for a distro or Windows version you actually tested on.

One thing that won't be merged: any change that lets mail send without a confirmed draft, or exposes key rotation or credential export as an MCP tool. That's the product, not an oversight — PLAN.md explains why.
